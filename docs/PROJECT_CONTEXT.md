# Контекст проекта и передача работы

Эта заметка сохраняет фактическое состояние проекта, важные ограничения и результаты проверок, чтобы быстро продолжить работу после паузы.

Контекст актуален на 2026-11-21. Пользователь планирует предоставить датасеты; когда они появятся, продолжить с их анализом и обучением, а не повторять настройку демо.

## Цель

По фотографиям с камер служебных автомобилей находить городскую инфраструктуру, объединять повторные наблюдения, оценивать состояние объектов и выдавать список для проверки или ремонта. Результаты: CSV, GeoJSON и HTML-карта.

## Что уже работает

- CLI: `run`, `analyze`, `prepare`, `train-det`, `train-clf`, `eval-det`.
- Пайплайн: чтение кадров, фильтрация качества, детекция, оценка состояния, геолокация, объединение повторных объектов и экспорт.
- Веб-интерфейс Streamlit: загрузка фото или выбор папки, необязательный GPS-трек, таблица, карта, кадры и скачивание результатов.
- `dummy` читает готовую YOLO-разметку рядом с кадрами и годится для проверки всего пути.
- `yolo` использует обученные веса `models/detector.pt`.
- GPS берётся из EXIF или CSV/GPX-трека. Если трек не даёт точного соответствия, координата помечается приблизительной. Если координат нет, место остаётся неизвестным; объект не удаляется из списка.
- При отсутствии весов классификатора состояние можно оценивать по геометрическим признакам.
- Этапные логи содержат идентификатор запуска; подробные логи включаются через `MGTS_LOG_LEVEL=DEBUG`.

## Приёмка датасета и обучение

Реальных данных пока нет. Когда они появятся, первый запуск — только анализ и отчёт, без обучения:

1. Скопировать исходники в `data/raw/`, не изменяя оригиналы.
2. Выполнить `mgts analyze --dataset data/raw`.
3. До `prepare` сверить `configs/classes.yaml` с разметкой: имена классов и их порядок/ID должны совпадать точно. Несовпадение может дать успешно завершившееся, но неверное обучение.
4. Проверить, что имена файлов позволяют `dataset.group_by: sequence` объединять соседние кадры одной серии; иначе похожие кадры могут попасть одновременно в train и val и завысить метрики.
5. Показать пользователю отчёт анализа и найденные несоответствия. На этом этапе остановиться: не запускать `prepare`, `train-det` или `train-clf`, пока пользователь не подтвердит следующий шаг.

После подтверждения:

1. Согласовать исправления `configs/classes.yaml` и `dataset.group_by`, выполнить `mgts prepare --src data/raw --fmt auto` и проверить split на утечки.
2. Детектор обучается на рамках и классах объектов. Для этого нужны YOLO, COCO, VOC или CSV-разметка и базовые веса `models/yolov8s.pt`; на CPU допустимы `models/yolov8n.pt`. GPU рекомендуется. При `device: auto` код выбирает для CPU более лёгкий режим (640 px, 15 эпох); ручной `device: cpu` использует настроенные `imgsz` и `epochs`, что может быть очень медленно.
3. После обучения выполнить `mgts eval-det --split val`, изучить recall по каждому классу, особенно редким, и вручную проверить ошибки на реальных кадрах. По проектному приоритету recall дефектов важнее ложных тревог.
4. Отдельно откалибровать на реальных примерах пороги размытия, наклона и трещин, а также высоту, наклон и поле зрения камеры для GPS-проекции. Это ручная проверка по изображениям и фактическим параметрам камеры; обучение её не выполняет.

Оценка состояния не является частью обучения детектора: геометрические эвристики работают по настроенным порогам. `mgts train-clf` — отдельный необязательный шаг, возможный только при наличии размеченных кропов `ok` и дефектов. Без них эвристики остаются непроверенными на реальных данных.

## Основные команды

Установка и демо описаны в [`README.md`](../README.md). Минимальная последовательность:

```bash
make install-dev # или make install для UI и обучения моделей
source .venv/bin/activate
make demo-data
make e2e
make test
```

Для UI после `make install` выполнить `make app`.

Запуск на данных пользователя после подготовки и обучения:

```bash
mgts run --input data/raw/images --track data/raw/frames.csv --output outputs/real-run --backend yolo
```

Если GPS-трека нет, убрать `--track data/raw/frames.csv`. GPS будет взят из EXIF, если доступен; иначе место останется неизвестным.

## Важные ограничения и предосторожности

- Успешный `make e2e` подтверждает интеграцию, но использует `dummy` и готовую разметку. Он не измеряет точность YOLO.
- Базовые веса YOLO сами по себе не распознают целевые классы проекта; для этого необходимы обучение и проверка на размеченных данных.
- Веса моделей локальные и не хранятся в git. Не удалять их при очистке репозитория.
- ZIP-архив GitHub не содержит `.git` и не сообщает точный commit. При передаче архива указывать SHA исходного коммита отдельно; для текущей рабочей копии проверять версию командами `git rev-parse HEAD` и `git status --short`.
- Версии зависимостей фиксируются в `uv.lock`; установка через Makefile использует этот lock-файл.
